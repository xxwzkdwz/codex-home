# Set up Codex Home

Resolve the plugin root two directories above this skill. Read `../../README.md` for platform-specific paths and supported configuration fields. This is a local desktop/CLI integration, not a hosted universal smart-home service.

1. Inspect the current installation and available tools. Codex Home needs Node.js 22+ and an existing reachable Mosquitto-compatible MQTT broker plus Zigbee2MQTT and paired lights. It does not require a separate home-control application or model API key. Do not install/reset a Zigbee network just because the plugin is unconfigured.
2. If runtime dependencies are missing in the installed copy, run `npm ci --omit=dev --ignore-scripts --no-audit --no-fund` in that plugin root. Do not substitute an old checkout's path.
3. Use `node src/cli.mjs init` from the plugin root to create a private empty configuration without overwriting an existing file. Alternatively, to reuse a device registry, use the owner's explicitly selected local file and run `node src/cli.mjs import-registry <absolute-devices.json-path>`. The registry must contain only `version: 1` and a `devices` array matching the documented light schema. This copies the device allowlist into separate local settings; it does not read or copy Zigbee keys or modify the source registry. An existing destination is never overwritten: choose import instead of init, or explicitly select a new destination with `--config`.
4. Guide the owner to edit their private configuration with their broker and exact light topics. Use `examples/config.example.json` only as a synthetic reference; its device is disabled and `state_confirmation` is `unverified`. Do not paste real config or credentials into chat. Passwords are supplied by owner-controlled environment variables or a separate owner-only file. Never ask for passwords, network keys or backups in conversation. Keep broker TLS verification enabled.
5. For 0.1.2, existing configurations without `state_confirmation` deliberately remain read-only. Follow the runtime README's confirmation/migration section: only standard default-endpoint single-channel lights are eligible. Verify the owner's compatible Z2M version and agree on scoped gateway changes before preparing correlated reads, preserving existing filters and network settings. Do not set `correlated_read` merely to bypass `STATE_CONFIRMATION_REQUIRED`, disable safeguards, or automatically restart a working gateway. Generic `state` GET/SET support alone is insufficient. No groups, endpoint suffixes or vendor-private state emulation.
6. Run `node src/cli.mjs check` (read-only) or use `home_health`. A healthy broker/bridge does not prove device control. Use `home_list_devices`; a `home_status` read is appropriate within the owner's setup or connectivity-check request and needs no separate permission. Correlated mode's `/set` wrapper carries a fixed read, not a switch command. Only `correlated_device_read` with freshness true and outcome confirmed passes its preflight. Unverified reports do not clear unknown outcomes. On failure diagnose compatibility/filters without falling back to ordinary state. A real ON/OFF test requires the user to authorize that light action and any intended restoration; setup alone is not permission to flash the home lights.

Default MQTT is loopback. Non-loopback plaintext needs the owner's explicit acceptance of trusted-LAN risk before `allow_insecure_lan` is enabled; recommend `mqtts` for authenticated remote brokers. Do not expose an unauthenticated broker on the internet. On macOS/Linux the config, password and custom CA files must belong to the current user and have mode 0600; Windows relies on owner-managed file ACLs.

Offline bridge: inspect only task-relevant process/port/serial diagnostics. If the coordinator is unplugged or a path changed, explain that evidence and ask the owner to reconnect/confirm the intended hardware. Preserve existing keys, PAN, pairing database and working services. Do not automatically restart, re-pair, remove devices or change serial settings.

Install/update through the repository's installer or Codex's marketplace commands, not by overwriting the user's entire Codex configuration. After installation the owner can use a new Codex chat/session to load tools; the current session can finish read-only validation through the updated installed CLI. Do not create a new chat on the owner's behalf without a request. A successful simulated test is not real-device acceptance; say exactly which layer passed.
